# ADR-003: Soft-Delete over Hard Delete

**Status:** Accepted

## Context

When a doctor leaves, the system needs removal handling. Hard delete destroys all data. Soft-delete preserves audit trail and historical appointments.

## Decision

Use `is_active` boolean field on doctors table for soft-delete. Hard delete is restricted to admin-only data cleanup.

## Alternatives

1. **Hard delete** — Breaks referential integrity with appointments. No audit trail.
2. **Archive table** — Complex implementation. Duplicate schema.
3. **Soft-delete with is_active (chosen)** — Simple, reversible, preserves integrity, follows existing DensCare pattern.

## Advantages

- Data preservation — historical appointments remain linked
- Reversible — deactivated doctors can be reactivated
- Audit trail — deactivation timestamp and user tracked
- Follows existing DensCare pattern (Patient, Appointment models)

## Disadvantages

- All queries must filter by is_active
- Data accumulates (negligible for MVP scale)
- Cannot cascade delete (intentional)

## Consequences

- All repository list queries filter by is_active
- Admin can hard-delete via direct DB if needed
- GET returns 404 for deactivated doctors
- Future reporting can include deactivated doctors for historical analysis
