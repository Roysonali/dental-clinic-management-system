# ADR-001: DoctorProfile as Separate Entity

**Status:** Accepted

## Context

DensCare currently represents doctors solely through User records with DOCTOR-family roles. This lacks structured fields for specialization, schedule, consultation fee, and other doctor-specific data. Two options: add columns to users table, or create a separate DoctorProfile entity.

## Decision

Create a new `doctors` table with 1:1 FK to `users.id`.

## Alternatives

1. **Add columns to users table** — Simpler but pollutes User model. Non-doctors have null doctor fields.
2. **JSONB in users** — Flexible but not queryable, no type safety.
3. **Separate DoctorProfile (chosen)** — Clean separation, independent lifecycle, follows existing DensCare pattern (Patient is separate from User).

## Advantages

- Clean separation of concerns — User module unchanged
- Doctor-specific fields don't pollute User model
- Independent lifecycle — deactivate doctor without affecting User login
- Indexable and queryable with proper SQL types

## Disadvantages

- Join overhead when querying doctor + user data
- Additional table
- User must exist before DoctorProfile

## Consequences

- All Doctor Management features reference doctors table
- Appointments module continues to reference users.id (see ADR-004)
- New migration required
